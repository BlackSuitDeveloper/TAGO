# TAGO 백엔드 개선 가이드

핵심 로직(대기열·Redis·예매·결제·실시간 좌석)과 예외 처리, 그리고 서비스를 열기 전에 반드시 고쳐야 하는 문제를 정리한 문서입니다.
**코드를 대신 고쳐 주는 문서가 아니라, 무엇이 왜 위험한지와 어떻게 고민해서 고칠지를 안내하는 문서**입니다. 각 항목에 "고민해 볼 질문"을 넣었으니 팀에서 먼저 토론한 뒤 구현하세요.

## 0. 읽는 법

- 근거는 클래스·메서드 이름으로 적었습니다(줄 번호는 바뀌므로). 근거 표기는 두 가지입니다.
  - **[확인]** 코드를 읽거나 실제 DB·앱을 띄워서 재현한 것
  - **[가설]** 코드 구조상 그럴 가능성이 높지만 부하·장애 상황에서 직접 확인이 필요한 것
- 심각도
  - **S1** 서비스를 열기 전에 반드시 고친다 (보안 사고, 돈·좌석이 틀어짐)
  - **S2** 사용자가 늘면 반드시 터진다
  - **S3** 품질과 유지보수
- 상태: **해결**(이미 PR 로 반영) / **미해결**

## 2. 대기열과 Redis (가장 먼저 고민할 영역)

### 2.1 먼저 "대기열이 무엇을 보호하는가"를 정하세요

코드를 보기 전에 아래 네 가지를 문장으로 정의해야 합니다. 정의 없이 구현하면 지금처럼 **동작은 하지만 아무것도 보장하지 않는** 코드가 됩니다.

1. **무엇을 보호하나?** 좌석 선점 API(`POST /reservation`)와 그 뒤의 DB. 대기열은 "한꺼번에 몰리는 선점 요청의 수"를 제한하는 문지기입니다.
2. **불변 조건(항상 참이어야 하는 규칙)**
   - I1. 입장권이 없는 사용자는 좌석을 선점할 수 없다.
   - I2. 한 열차에서 동시에 선점할 수 있는 사용자는 N 명 이하다.
   - I3. 먼저 줄 선 사람이 먼저 들어간다.
   - I4. 입장권은 유효시간이 지나면 반드시 사라진다.
   - I5. Redis 가 죽었을 때의 정책이 정해져 있다.
3. **누가 입장권을 쓰나?** 입장권은 "어떤 회원이, 어떤 열차에" 대해서만 유효해야 합니다.
4. **입장권을 언제 반납하나?** 결제를 끝냈거나 취소했을 때 바로 슬롯을 돌려줘야 처리량이 나옵니다.

### 2.2 지금 구조 (QueueService)

- 열차마다 Redis 키 두 개: 대기 줄(`tago:queue:{scheduleSeq}`, ZSET, 점수 = 진입 시각) 과 입장자(`tago:queue:active:{scheduleSeq}`, ZSET, 점수 = 만료 시각).
- 입장 가능하면 입장자 ZSET 에 넣고, 아니면 대기 줄에 넣은 뒤 순번을 돌려줍니다. 진입과 일괄 입장은 Lua 스크립트라 **원자적**입니다 (이 부분은 잘 만들어져 있습니다).
- 3초마다 스케줄러가 만료된 입장자를 지우고 빈 슬롯만큼 대기 줄 앞사람을 입장시킵니다.
- 전역 집합 `tago:queue:admitted` 와 열차 목록 집합 `tago:queue:schedules`, 토큰 메타 `tago:queue:meta:{token}` 를 함께 씁니다.

### Q-1. 대기열이 예매에 연결되어 있지 않다 [확인] S1

- **근거**: `ReservationController.holdSeats`, `ReservationService.holdSeats`, `PaymentService.processPayment` 어디에도 대기열 토큰 검사가 없습니다. 프론트가 대기열 호출에 실패하면 그냥 예매 화면으로 넘어가는 코드(`SchedulePage`)도 있습니다.
- **어떻게 터지나**: `POST /api/v1/reservation` 을 직접 호출하면 대기열을 우회합니다. 대기열이 보호하려던 대상이 보호되지 않습니다.
- **고민해 볼 질문**
  - 입장권은 어디에 실어서 보낼까요(헤더, 바디)? 서버는 어디서 검사할까요(인터셉터, 서비스)?
  - 선점이 성공하면 입장권을 연장할지, 소비할지, 유지할지? 결제까지 끝나면 슬롯은 언제 돌려줄지?
  - 대기열을 거치지 않는 정상 경로가 있는지(관리자, 한산한 열차)? 있다면 어떻게 구분할지?
- **방향**
  1. 선점 요청에 `X-Queue-Token` 을 필수로 받고, **Lua 한 번으로** "입장자 ZSET 에 있고 만료 전이고 이 회원·이 열차의 토큰인지"를 검사합니다.
  2. 선점 성공 시 만료를 선점 유효시간만큼 늘리고, 결제·취소·만료 시 입장자에서 제거(`ZREM`)해서 슬롯을 즉시 반납합니다.
  3. 열차가 한산할 때까지 대기열이 필요 없다면, "입장자 수 < 한도"일 때 서버가 자동으로 입장권을 발급하게 하면 프론트는 항상 같은 경로를 씁니다.
- **확인 방법**: 토큰 없이 선점 → 거부. 남의 토큰으로 선점 → 거부. 다른 열차 토큰으로 선점 → 거부.

### Q-2. 입장 완료 토큰이 영원히 유효하다 [확인] S2

- **근거**: `QueueService` 가 입장시킬 때 전역 집합 `tago:queue:admitted` 에 토큰을 `SADD` 하지만, 입장자 ZSET 의 만료(`ZREMRANGEBYSCORE`)와 달리 이 집합에서는 **지우는 코드가 없습니다**. `checkQueueRank` 는 이 집합에 있으면 "입장 차례입니다"라고 답합니다.
- **어떻게 터지나**: (1) Redis 메모리가 계속 늘어납니다. (2) 입장 시간이 지난 토큰도 영원히 "입장됨"으로 보여서, Q-1 을 고쳐도 이 집합을 그대로 쓰면 **만료된 권한이 되살아납니다.**
- **방향**: 전역 집합을 없애고, 입장 여부를 **입장자 ZSET 의 점수(만료 시각)로 판단**하세요 (`ZSCORE active token` 이 현재 시각보다 크면 입장). 상태가 한 곳에만 있으면 지우는 곳도 한 곳입니다.
- **확인 방법**: 토큰 TTL 을 3초로 줄여 입장 → 4초 뒤 조회하면 "입장 아님"이어야 합니다. Redis 키 개수가 시간이 지나도 늘지 않는지 확인.

### Q-3. Redis 장애 시 인메모리로 조용히 바뀐다 [확인] S2

- **근거**: `QueueService.enterQueue`/`checkQueueRank` 가 예외를 잡아 로그만 남기고 인메모리 맵으로 처리합니다. 이 맵은 **서버 한 대 안에서만** 유효하고, 열차 구분 없이 전체 인원으로 입장을 판단하며(`inMemoryQueue.size() <= maxActiveUsers`), 스케줄러는 용량 확인 없이 3초마다 30명을 입장시키고, 입장 집합은 줄지 않습니다.
- **어떻게 터지나**: Redis 가 죽으면 대기열 규칙이 **모르는 사이에 다른 규칙으로** 바뀝니다. 서버가 두 대면 서로 다른 대기열을 가집니다. 장애 때 가장 몰리는 상황에서 보호 장치가 가장 약해집니다.
- **고민해 볼 질문**
  - Redis 장애 시 **예매를 막는 것(fail-closed)** 과 **그냥 통과시키는 것(fail-open)** 중 무엇이 이 서비스에 덜 나쁜가요? DB 를 지키는 것이 목적이라면 통과는 위험합니다.
  - 막는다면 사용자에게 어떤 메시지를 줄까요? (`ErrorCode` 에 코드를 추가하세요: 예 6000번대 대기열.)
- **방향**: 가장 단순하고 안전한 쪽은 **fail-closed**(503 + "잠시 후 다시 시도")입니다. 인메모리 대체를 유지하고 싶다면 (1) 규칙을 Redis 와 똑같이 맞추고 (2) 대체 모드로 들어갔다는 사실을 로그·메트릭으로 알리고 (3) 한 대 서버에서만 쓰는 임시 모드임을 문서화하세요.

### Q-4. 떠난 사용자가 슬롯을 차지한다 (유령 토큰) [가설] S2

- **근거**: 스케줄러는 줄 앞에서부터 **살아 있는지 확인하지 않고** 입장시킵니다. 사용자가 창을 닫아도 대기 줄 항목은 남고, 입장하면 TTL(5분) 동안 슬롯을 차지합니다.
- **어떻게 터지나**: 이탈이 많은 인기 열차에서 입장자 수가 가득 찬 채 실제 예매는 거의 일어나지 않습니다.
- **고민해 볼 질문**: "살아 있다"는 어떻게 정의할까요? (마지막 폴링 시각이 N초 이내) 폴링 간격은 서버가 정해 줄까요?
- **방향**: 조회(폴링) 때마다 토큰의 `lastSeen` 을 갱신하고, 입장시키기 전에 `lastSeen` 이 오래된 항목을 줄에서 지웁니다. 입장 후에는 입장 TTL 을 짧게(예: 선점 화면 진입 확인 후 연장) 두는 방법도 있습니다.

### Q-5. 토큰이 회원·열차와 묶여 있지 않다 [확인] S2

- **근거**: `enterQueue` 는 호출할 때마다 새 `UUID` 를 만들어 줄에 넣습니다. `memberId` 는 받지만 쓰지 않습니다. `META` 키는 대기 중일 때만 저장하고 30분 뒤 사라져서, 그 뒤 순번 조회는 항상 "1번째"를 돌려줍니다.
- **어떻게 터지나**: 한 사용자가 여러 번 눌러 줄을 부풀리고 슬롯을 여러 개 차지할 수 있습니다. 한 사용자가 200명을 채울 수 있습니다.
- **방향**: 회원 + 열차 당 입장권을 하나로 제한합니다(`SET key NX`, 또는 `HSETNX`). 이미 있으면 **기존 토큰을 그대로 돌려주는(멱등) 진입**으로 만듭니다. 토큰 메타(회원, 열차, 진입 시각)는 해시 하나에 저장하고 TTL 을 대기 시간보다 길게 둡니다.

### Q-6. Redis 설정이 비어 있다 [가설] S2

- **근거**: `application.properties` 에는 호스트·포트·DB 번호뿐입니다. 비밀번호, 명령 타임아웃, 연결 타임아웃, 풀 설정이 없습니다. Lettuce 의 기본 명령 타임아웃은 길어서(공식 기본값 확인 필요), Redis 가 응답하지 않을 때 요청 스레드가 오래 붙잡힐 수 있습니다.
- **방향**: `spring.data.redis.timeout`(예: 500ms~1s), `connect-timeout`, `password` 를 설정하세요. 키 이름 규칙(예: `tago:{도메인}:{종류}:{id}`)과 **모든 키의 TTL 이 있는지** 점검하세요. 이메일 인증용 키(`VERIFY:*`, `TOKEN:*`, `VERIFIED:*`)는 접두어 규칙이 달라 대기열 키와 다르게 보이는데, 같은 규칙으로 통일하세요.
- **참고**: `RedisConfig` 는 설정이 아니라 헬퍼 클래스인데 `@Configuration` 이 붙어 있습니다. `@Component` 로 바꾸거나 이름을 `RedisValueStore` 처럼 바꾸는 편이 의도가 드러납니다.

### Q-7. 스케줄러가 열차 목록을 3초마다 전부 훑는다 [확인] S3

- **근거**: `scheduleAdmitQueue` 가 `SMEMBERS tago:queue:schedules` 로 열차 전체를 읽고 열차마다 Lua 를 호출합니다. 서버가 여러 대면 모두 같은 일을 합니다(Lua 가 원자적이라 **틀리지는 않지만** 낭비입니다).
- **방향**: 대기 줄이 있는 열차만 처리하고, 처리 대상이 많아지면 `ZSET` 로 "다음 처리 시각"을 관리하세요. 지금 규모에서는 급하지 않습니다.

### 이 영역을 테스트하는 법

- **로컬 Redis** (Docker 또는 Testcontainers) 로 통합 테스트: 1,000개 스레드가 동시에 진입 → 입장자 수가 한도를 넘지 않는지, 순번이 겹치지 않는지.
- 입장 TTL 을 짧게 줄여 **만료와 슬롯 반납**을 확인.
- Redis 를 중간에 끄고 **정책(fail-closed)대로 동작**하는지 확인.
- Lua 스크립트는 `redis-cli --eval` 로 단독 실험해 보면 이해가 빠릅니다.

## 3. 좌석 선점·예매·결제 (돈과 좌석이 걸린 영역)

### 3.1 먼저 상태 기계를 그리세요

예약 상태는 `HELD(선점) → CONFIRMED(결제 완료)` 또는 `HELD → CANCELLED(사용자 취소/만료)`, 그리고 `CONFIRMED → CANCELLED(환불)` 입니다.
**허용되는 전이를 표로 그리고, 각 전이를 하나의 조건부 UPDATE 로** 만드는 것이 이 영역의 핵심입니다.

| 현재 → 다음 | 누가 | 조건 |
|---|---|---|
| (없음) → HELD | 선점 API | 좌석이 비어 있고, 입장권이 있고, 출발 전 |
| HELD → CONFIRMED | 결제 API | 본인, 만료 전, 금액 일치 |
| HELD → CANCELLED | 사용자 / 스케줄러 | 본인 또는 만료 |
| CONFIRMED → CANCELLED | 환불 API | 본인, 출발 전, 결제 취소 처리 |

### BIZ-1. 상태 전이에 가드가 없다 [확인] S1

- **근거**: `reservation_mapper.xml` 의 `confirmReservation` 과 `updateReservationStatus` 는 `WHERE reservation_seq = ?` 만 있고 **현재 상태를 보지 않으며**, 서비스는 영향받은 행 수를 확인하지 않습니다. 서비스는 먼저 조회하고(상태 확인) 나중에 갱신하는데 그 사이에 잠금이 없습니다.
- **어떻게 터지나**
  1. 결제 버튼 더블클릭 → 두 요청이 모두 `HELD` 를 읽고 **결제 행을 두 개** 만들고 확정합니다.
  2. 결제 요청이 만료 검사를 통과한 직후 스케줄러가 같은 예약을 `CANCELLED` + 좌석 삭제로 바꾸고, 결제가 `CONFIRMED` 로 덮어씁니다. **결제는 됐는데 좌석은 다른 사람에게 팔릴 수 있습니다.**
  3. 사용자 취소와 결제가 겹쳐도 같습니다.
- **고민해 볼 질문**
  - "확인 후 갱신" 대신 "조건을 붙여서 갱신하고 결과를 확인"하면 어떻게 되나요? (`UPDATE ... SET status='CONFIRMED' WHERE reservation_seq=? AND status='HELD' AND expires_at > now()` 의 영향 행 수)
  - 행 수가 0 이면 어떤 에러(410 만료, 409 이미 처리됨)로 바꿀까요? (`ErrorCode` 에 있습니다.)
  - 같은 결제 요청이 두 번 와도 **한 번만** 처리되게 하려면(멱등)? 요청에 멱등 키를 받고 `payment` 에 UNIQUE 를 둘까요?
- **방향**: ① 모든 상태 전이 UPDATE 에 `AND status = '기대 상태'` 를 붙이고 영향 행 수가 기대와 다르면 예외 ② 결제와 취소 시작에서 예약 행을 `SELECT ... FOR UPDATE` 로 잠그는 방법 ③ `payment(reservation_seq)` 에 승인 상태 UNIQUE.
- **확인 방법**: 같은 예약으로 `/payment` 를 동시에 10번 호출 → 결제 행이 1개인지. 결제와 만료를 동시에 일으키는 스레드 테스트(`SeatConcurrencyTest` 를 참고해서 작성).

### BIZ-2. 호차 하나로 여러 좌석을 선점한다 [확인] S1

- **근거**: `ReservationRequestDTO` 는 `carNo` 하나와 `seatList` 입니다. `ReservationService.holdSeats` 는 같은 `carNo` 로 모든 좌석을 찾습니다. 프론트도 첫 좌석의 호차를 전체에 씁니다. 좌석 번호(`3A`)는 모든 호차에 있습니다.
- **어떻게 터지나**: 5호차 `3A` 와 7호차 `3B` 를 고르면 **5호차 `3A`, `3B` 가 잡히고 에러도 없습니다.** 사용자는 엉뚱한 좌석 값을 결제합니다.
- **방향**: 요청을 `seats: [{carNo, seatNo}]` 로 바꾸고 좌석마다 자기 호차로 검증하세요(프론트 수정 필요). 또는 한 번에 한 호차만 허용하고 프론트에서 막는 임시 방편을 두세요(근본 해결은 아님).

### BIZ-3. 취소와 환불이 불완전하다 [확인] S2

- **근거**: 다좌석 예매는 **좌석마다 예약 행이 하나씩** 생기고, 묶는 기준(주문)이 없습니다. 결제 행은 대표 예약 하나에만 걸리고 총액이 들어갑니다. `PaymentMapper` 의 `updatePaymentStatus`(미사용이라 삭제됨)처럼 **결제 상태를 바꾸는 코드가 사실상 없어서** 취소해도 결제 행은 `APPROVED` 로 남습니다. `cancelReservation` 은 `CONFIRMED` 인 예약과 **출발한 뒤의 예약**도 취소합니다.
- **어떻게 터지나**: 좌석 2개 중 1개만 취소하면 총액(2석분)이 그대로 남습니다. 환불 금액과 내역이 맞지 않습니다. 내 승차권 목록에서 대표 예약이 아닌 좌석은 `ticketNumber` 가 비어 있습니다(`payment` 를 대표 예약으로만 조인).
- **고민해 볼 질문**: "주문(order)" 이라는 개념이 필요하지 않나요? 한 번의 결제로 묶이는 예약들을 하나로 보면 환불, 영수증, 목록이 모두 단순해집니다.
- **방향**: `booking`(주문) 테이블을 두고 `reservation.booking_id`, `payment.booking_id` 로 묶습니다. 취소 시 결제 상태(`REFUNDED`)도 함께 바꾸고, 출발 시각 이후에는 취소를 거부합니다.

### BIZ-4. 선점 검증이 부족하다 [확인] S2

- **근거**: `holdSeats` 는 열차가 존재하는지만 봅니다. 열차 `status`, 예매 오픈 시각(`booking_open_at`), **출발 시각**은 확인하지 않습니다. `seatList` 길이 제한이 없고, 같은 좌석을 두 번 넣는 경우도 막지 않습니다. 좌석을 요청한 순서대로 넣습니다.
- **어떻게 터지나**: (1) 이미 출발했거나 아직 열리지 않은 열차에 선점할 수 있습니다. (2) 한 계정이 935석을 5분 동안 통째로 잡고 반복할 수 있습니다. (3) 두 사용자가 `1A,1B` 와 `1B,1A` 를 동시에 요청하면 서로 상대의 잠금을 기다리는 **교착(deadlock)** 이 나고 한쪽이 500 이 됩니다.
- **방향**: 열차 상태·오픈·출발 시각 검증, 좌석 수 상한(예: 4~6석)과 회원당 동시 선점 수 상한, 좌석 목록을 정렬·중복 제거 후 처리, 교착(`40P01`)을 409 로 변환.

### DB-1. UNIQUE 제약이 전제인데 DDL 이 없다 [확인] S1

- **근거**: 이중 예매 방지는 `seat_mapper.xml` 의 `INSERT ... ON CONFLICT (schedule_seq, car_no, seat_no) DO NOTHING` 에 기대고 있습니다. 이 제약이 DB 에 **실제로 있는지 저장소 어디에도 나와 있지 않습니다.** 없으면 선점이 에러로 실패하거나 중복이 생길 수 있습니다.
- **방향**: 스키마를 SQL 파일로 저장소에 두세요(`db/` 폴더에 번호 붙은 마이그레이션, 예: `001_member_role.sql` 처럼). 이상적으로는 Flyway 를 도입합니다. **UNIQUE 제약은 가장 먼저 DDL 로 못 박아야 합니다.**
- **참고(실제 DB 로 돌려 본 결과)**: 이 저장소의 코드로 스키마를 역산해서 PostgreSQL 에 올려 전체 API 를 돌려 보니, 찜(`wishlist_seq` 컬럼 필요), 취소(`reservation.seat_seq` 가 NULL 이어야 함), 탈퇴(회원 FK 정책) 에서 가정이 틀리기 쉬웠습니다. DDL 이 없으면 팀원마다 DB 가 달라집니다.

### DB-2. 찜 추가가 동시에 누르면 깨진다 [확인] S2

- **근거**: `wishlist_mapper.xml` 의 `insertWish` 가 `(SELECT COALESCE(MAX(wishlist_seq), 0) + 1 FROM wishlist)` 로 번호를 매깁니다. 읽고 +1 하는 사이에 다른 요청이 같은 번호를 만들 수 있고, 테이블이 커지면 매번 전체를 훑습니다.
- **방향**: 시퀀스/`GENERATED ALWAYS AS IDENTITY` 컬럼으로 바꾸세요. `(member_id, schedule_seq)` UNIQUE 를 두고 `ON CONFLICT DO NOTHING` 으로 중복 추가를 멱등하게 만드세요.

### DB-3. 인덱스·제약·삭제 정책 [가설] S2

- **근거**: DDL 이 없어서 확인할 수 없지만, 코드의 조회 패턴상 아래가 필요합니다.
  - `seat(schedule_seq, car_no, seat_no)` UNIQUE (선점), `seat(schedule_seq)` (좌석 수 집계)
  - `reservation(status, expires_at)` (만료 해제), `reservation(member_id, reserved_at)` (내 승차권), `reservation(seat_seq)`
  - `schedule(depplandtime)`, `schedule(trainno, depplacename, arrplacename, depplandtime)` (동기화 중복 확인)
  - `payment(reservation_seq)`
- `schedule_mapper.xml` 의 시간표 쿼리는 행마다 `(935 - (SELECT COUNT(*) FROM seat ...))` 를 계산하는 **상관 서브쿼리**이고 `935` 는 `SeatTemplateGenerator` 상수와 중복입니다. 열차가 많아지면 느려지므로 `seat(schedule_seq)` 인덱스는 필수이고, 필요하면 잔여석 수를 컬럼으로 두는 것도 고민하세요.
- **탈퇴**: 회원 삭제 시 예약·찜·결제를 어떻게 할지 정해야 합니다(FK `ON DELETE` 정책, 또는 삭제 대신 비활성화). 정하지 않으면 예약이 있는 회원은 탈퇴가 실패합니다.
- **방법**: 실제 쿼리에 `EXPLAIN ANALYZE` 를 걸어 보고 인덱스를 정하세요.

## 4. 시간과 만료 (TIME-1, SCH-1)

### TIME-1. 시계가 둘이고 선점 시간이 하드코딩이다 [확인] S2

- **근거**: 선점 만료 시각은 앱이 `LocalDateTime.now()` 로 계산해서 저장합니다. 만료 해제 쿼리는 `expires_at < NOW()` 로 **DB 시계**와 비교합니다. 결제는 다시 **앱 시계**로 만료를 판단합니다. 선점 시간은 `HOLD_TTL_MINUTES = 5` 상수이고 만료 안내 문구("5분")도 고정입니다.
- **어떻게 터지나**: 앱 서버와 DB 서버의 시계·시간대가 다르면 선점이 즉시 만료되거나 영원히 안 풀립니다. 선점 시간을 바꾸려면 코드와 문구를 모두 고쳐야 합니다. (프론트 화면은 서버가 준 `expiresAt - reservedAt` 으로 카운트다운을 그리므로 서버 값이 곧 사용자에게 보이는 시간입니다. 10분으로 하려면 서버 값만 바꾸면 됩니다.)
- **방향**: 시간의 기준을 하나로(보통 DB `now()` 또는 UTC `Clock`) 정하고, 선점 시간은 설정값(`tago.reservation.hold-minutes`)으로 빼서 에러 문구도 그 값을 쓰게 하세요. 응답에 남은 시간(`ttlSeconds`)을 함께 주면 프론트가 서버 시계에 의존하지 않습니다.

### SCH-1. 스케줄러 한 줄 서기 [확인] S2

- **근거**: Spring 기본값은 스케줄러 스레드 1개입니다. 5초마다 만료 해제(`autoReclaimExpiredHeldSeats`), 3초마다 대기열 입장(`scheduleAdmitQueue`), 새벽 3시 외부 API 동기화(`scheduledDailySlidingWindowSync`)가 **같은 스레드**에서 돕니다. 동기화가 외부 API 응답을 기다리며 멈추면 그동안 만료 해제와 대기열 입장도 멈춥니다.
- **어떻게 터지나**: 외부 API 가 느려지면 선점이 안 풀리고(다른 사용자는 409), 대기열 입장이 멈춥니다.
- **방향**: `spring.task.scheduling.pool.size` 를 늘리고(예: 3~5), 외부 호출에 타임아웃을 두세요(9장). 서버를 여러 대로 늘릴 계획이라면 **한 번에 한 대만 실행**해야 하는 작업(동기화, 만료 해제)을 어떻게 보장할지(`SELECT ... FOR UPDATE SKIP LOCKED`, ShedLock, Redis 락)도 미리 고민하세요.
- **만료 해제 자체도 개선 여지**: 한 건씩 `UPDATE` + `DELETE` 를 반복합니다. `UPDATE ... WHERE status='HELD' AND expires_at < now() RETURNING seat_seq` 한 번과 좌석 일괄 삭제로 바꾸면 빠르고, 조건부라 결제와 경합해도 안전합니다(BIZ-1 과 같이 해결).

## 5. 실시간 좌석 (SSE)

### SSE-1. 세 가지 문제 [확인] S2

1. **커밋 전에 전송한다.** `ReservationService.holdSeats` 가 트랜잭션 안에서 좌석마다 "HELD" 를 보냅니다. 3석 중 2번째에서 실패해 롤백돼도 1번째 좌석의 "선점됨" 이벤트는 이미 나가서 **취소되지 않습니다.**
2. **풀림 이벤트가 없다.** 사용자 취소(`TODO` 로 남아 있음)와 만료 해제에서는 `AVAILABLE` 을 보내지 않아서 화면의 좌석이 계속 회색입니다. 프론트는 이미 `AVAILABLE` 이벤트를 처리하도록 되어 있습니다.
3. **예외를 `IOException` 만 잡는다.** 이미 닫힌 연결에 보내면 `IllegalStateException` 이 날 수 있고, 그러면 **예매 트랜잭션이 500 으로 롤백**될 수 있습니다.
- **방향**: 커밋 **후**에 전송(`@TransactionalEventListener(phase = AFTER_COMMIT)`), 전송 예외는 모두 잡아서 연결만 정리, 취소·만료·확정에서도 전송.

### SSE-2. 서버가 여러 대면 동작하지 않는다 / 연결 관리 [가설] S2

- **근거**: 연결(`SseEmitter`)은 서버 메모리에 있어서 **다른 서버에서 일어난 선점은 이 서버의 구독자에게 전달되지 않습니다.** 구독자가 모두 떠난 열차의 빈 목록이 맵에 남고, 연결 개수 제한이 없으며, 30분 타임아웃 외에 주기적 확인 신호(heartbeat)가 없습니다. nginx 같은 프록시는 한동안 데이터가 없으면 연결을 끊습니다(`SEAT_UPDATE` 가 없는 한산한 열차).
- **방향**: 서버를 하나로 유지하는 것이 현실적입니다(그렇다면 문서에 명시). 늘릴 계획이면 Redis Pub/Sub 로 이벤트를 모든 서버에 전달하세요. 30초마다 주석 이벤트(`: ping`)를 보내고, IP·열차당 연결 수를 제한하세요.

## 6. 보안

### SEC-1. 남의 비밀번호를 바꿀 수 있다 [확인] S1

- **근거**: `AuthController` 의 비밀번호 재설정은 3단계입니다. (1) 이름·이메일 확인 후 코드 발송 (2) 코드 확인 후 **재설정 토큰 발급(토큰은 이메일에만 묶임)** (3) `resetPassword` 가 `dto.getId()` 로 **요청 본문의 아이디**를 받아 그 회원의 비밀번호를 바꿉니다. 토큰과 아이디의 관계를 검사하지 않습니다. 가입 시 이메일 인증도 없습니다.
- **어떻게 터지나**: 공격자가 자기 계정(자기 이메일)으로 1~2단계를 통과해 토큰을 받고, 3단계에서 **피해자의 아이디**를 넣으면 피해자 비밀번호가 바뀝니다. 아이디는 `GET /member/checkId` 로 추측할 수 있습니다.
- **고민해 볼 질문**: 토큰은 무엇을 증명해야 할까요? ("이 사람이 이 **계정**의 이메일 소유자다")
- **방향**: 토큰 발급 시 Redis 에 `TOKEN:RESET_PW:{token} = 회원 아이디` 를 저장하고, 3단계는 **본문의 아이디를 무시하고** 토큰에 저장된 아이디만 사용하세요. 2단계에서도 "아이디+이메일" 쌍을 키에 넣으세요.
- **확인 방법**: 계정 A 의 토큰으로 계정 B 의 비밀번호 변경 시도 → 거부되어야 합니다 (테스트로 남기세요).

### SEC-2. 인증번호를 무한 시도할 수 있다 [확인] S1

- **근거**: 6자리 숫자 코드(`SecureRandom` 은 올바름)를 5분 안에 **횟수 제한 없이** 맞춰 볼 수 있습니다(`MailService`). 아이디 찾기와 비밀번호 재설정의 확인·발송 API 는 모두 공개입니다. 일치하지 않는 정보는 404, 일치하면 200 + 메일 발송이라 **가입된 (아이디, 이메일) 쌍을 확인하는 수단**이 됩니다. 발송에 제한이 없어 특정 이메일로 **메일 폭탄**을 보낼 수 있습니다. 아이디 찾기 확인 응답은 마스킹한 값 옆에 **실제 아이디 전체**도 돌려줍니다(`id`, `maskedId`).
- **방향**: 실패 횟수를 Redis 에 세어(`INCR` + TTL) 5회 넘으면 코드를 폐기하고 일정 시간 잠그세요. 재발송에 쿨다운(60초)과 IP·이메일 단위 제한을 두세요. 존재 여부와 무관하게 같은 응답("가입된 정보라면 메일이 발송됩니다")을 주세요. 아이디 찾기는 전체 아이디를 응답이 아니라 **메일로** 보내세요.

### SEC-3. 마이페이지 비밀번호·이메일 변경 [확인] S2

- **근거**: `PUT /member/password` 는 이메일 인증만 거치고 **현재 비밀번호를 확인하지 않습니다.** `PUT /member` 는 인증 없이 **이메일을 바꿀 수 있고**, 이후 인증번호는 바뀐 이메일로 갑니다.
- **어떻게 터지나**: 토큰이 탈취되면(프론트는 `localStorage` 에 저장) 이메일을 바꾸고 → 인증번호를 받아 → 비밀번호를 바꿔 **계정을 영구 탈취**할 수 있습니다.
- **방향**: 비밀번호 변경에 현재 비밀번호를 요구하고, 이메일 변경은 새 이메일로 인증한 뒤에만 반영하세요.

### 그 밖의 보안 항목 [확인/가설] S2~S3

- **로그에 인증번호가 남는다 [확인]**: 메일 발송이 실패하거나 SMTP 설정이 없으면 `MailService` 가 **메일 본문(인증번호 포함)을 로그에 출력**하고, 응답은 "발송되었습니다"입니다. 로그를 읽을 수 있는 사람은 비밀번호를 재설정할 수 있습니다. 실패 시 에러를 돌려주고 본문은 로그에 남기지 마세요.
- **JWT**: 로그아웃·탈퇴·비밀번호 변경 후에도 발급된 토큰은 만료(기본 1시간)까지 유효합니다. 권한(ROLE) 변경도 토큰 만료 후에 반영됩니다. 필요하면 토큰 버전을 DB 에 두고 비교하거나 짧은 만료 + 리프레시 토큰을 검토하세요. 프론트가 토큰을 `localStorage` 에 두면 XSS 한 번에 탈취됩니다(`HttpOnly` 쿠키 방식 검토).
- **CORS**: `allowedOrigins("*")` 입니다. 프론트 주소만 허용하세요.
- **로그인 시도 제한 없음**: 계정·IP 단위 제한을 두세요.
- **계정 열거**: `GET /member/checkId` 는 가입 화면에 필요하지만 무제한 호출이 가능합니다. 요청 제한을 두세요.
- **입력 검증 없음**: 가입 시 아이디·이메일·전화번호 형식과 길이, 비밀번호 정책이 서버에서 검증되지 않습니다(EXC-1).

## 7. 예외 처리·검증·로깅 (EXC-1)

지금은 공통 응답(`ResWrapper`)과 에러 코드(`ErrorCode`), 전역 예외 처리기(`GlobalExceptionHandler`)가 있습니다. 이제 **무엇을 예외로 던질지**를 정해야 합니다.

1. **입력 검증 [확인]**: DTO 에 `@NotBlank`, `@Size`, `@Email`, `@Pattern` 을 붙이고 컨트롤러에 `@Valid` 를 쓰세요. 검증 실패는 `GlobalExceptionHandler` 에 `MethodArgumentNotValidException` 핸들러를 추가해 필드별 메시지를 주면 프론트가 필드 옆에 에러를 보여줄 수 있습니다.
2. **NPE 가 500 으로 나간다 [확인]**: 예를 들어 `AuthController.verifyFindIdCode` 는 `dto.getName().trim()` 을 검증 없이 호출합니다(이름 없이 호출하면 NPE). 외부에서 오는 값은 모두 `null` 가능성을 가정하세요.
3. **트랜잭션 경계 [확인]**: `@Transactional` 은 같은 클래스 안에서 호출하면 적용되지 않습니다(프록시 우회). 읽기 전용 조회에는 `readOnly = true` 를 쓰세요. 외부 API 호출을 트랜잭션 안에 넣지 마세요(이미 `sync` 에서는 뺐습니다).
4. **DB 예외 변환**: 지금은 무결성 위반을 전부 `DATA_CONFLICT(1005)` 로 돌려줍니다. 의미 있는 경우(좌석 중복, 아이디 중복)는 서비스에서 잡아서 **구체적인 에러 코드**로 바꾸세요(예: `DUPLICATE_MEMBER_ID`).
5. **에러 코드 추가 규칙**: 새 에러는 `ErrorCode` 의 해당 번호 대역에 추가하고 프론트가 구분해야 하는 것만 코드로 만드세요. 6000번대(대기열), 7000번대(외부 연동)는 비워 두었습니다.
6. **로그**: 개인정보(비밀번호, 인증번호, 토큰, 전체 이메일)를 남기지 마세요. 요청 단위 추적 ID(MDC) 를 넣으면 장애 때 한 요청을 따라가기 쉽습니다. 외부 API 오류에는 서비스 키가 URL 에 섞이지 않는지 확인하세요(9장).

## 9. 외부 API 연동 (공공데이터 TAGO)

### 이미 반영한 것

- **일정 일괄 저장**: 일정을 1건마다 "있는지 확인 + INSERT"(2N 번 쿼리)하던 것을 한 번의 `INSERT ... WHERE NOT EXISTS` 로 바꿨습니다.
- **트랜잭션 범위**: 외부 API 를 기다리는 동안 DB 트랜잭션(=커넥션)을 붙잡던 구조를 바꿨습니다.
- **역 캐시**: 갱신 중 빈 맵이 보이던 문제를 새 맵 통째 교체로 해결했습니다.
- **열차 마스터 upsert**: 일자마다 반복하던 것을 프로세스당 한 번으로.
- **구조**: 외부 연동(`openapi`)과 동기화(`sync`)를 분리했고, 좌석 템플릿을 `seat` 로 옮겼습니다.

### SYNC-1. 외부 호출 자체의 안정성 [확인] S2

- **[반영됨] 타임아웃**: `TagoApiClient` 에 연결 3초, 응답 10초 제한을 두었습니다(`tago.api.connect-timeout-ms`, `tago.api.read-timeout-ms`). 느린 서버 앞에서 호출이 제한 시간 안에 끝나는지 로컬 HTTP 서버로 테스트합니다.
- **[반영됨] 재시도**: 연결 실패, 제한 시간 초과, 5xx, 429 만 짧게 기다렸다가 다시 시도합니다(`tago.api.max-attempts` 기본 2회, `tago.api.retry-backoff-ms` 기본 500ms). 그 외 4xx 는 다시 시도해도 같으므로 재시도하지 않습니다.
- **[반영됨] 서비스 키 마스킹**: 오류 로그에서 `serviceKey=` 값과 키 원문·인코딩 값을 가립니다. (Spring 의 예외 문구는 요청 주소에서 쿼리스트링을 이미 빼서, 지금은 방어용 장치입니다. 다른 HTTP 라이브러리로 바꾸면 이 장치가 필요해질 수 있습니다.)
- **[남음] "실패"와 "데이터 없음" 구분**: 지금도 외부 호출이 끝내 실패하면 빈 목록을 돌려주므로, 호출하는 쪽에서는 "그날 열차가 없음"과 구분되지 않습니다. 실패를 결과에 담아(또는 예외로) 동기화 결과 메시지와 재실행 판단에 쓰도록 고민하세요.
- **페이지네이션 없음**: `numOfRows=500&pageNo=1` 고정입니다. 노선·날짜의 열차가 500건을 넘으면 잘립니다.
- **호출 수**: 역 동기화는 시·도 수만큼(약 17번) 호출한 뒤 필요한 역 15개만 남기고 버립니다. 역 정보는 거의 변하지 않으니 한 번 받아 저장하고 필요한 시/도만 호출하거나 시드 데이터로 두는 것이 낫습니다. 일정 동기화는 노선 수 × 날짜 수만큼 **순차** 호출합니다. 호출 한도(일일 쿼터)를 확인한 뒤 제한된 동시성(예: 4개)으로 병렬화할 수 있습니다. 한도를 모르는 상태에서 병렬화하면 차단당할 수 있습니다.
- **설정이 코드에 하드코딩**: `TagoRouteConfig` 의 노선, 역 주소, KTX 편성 매핑이 코드에 상수로 있습니다. 바뀔 수 있는 운영 데이터이므로 설정 파일이나 DB 로 옮기는 것을 고민하세요.
- **관리자 모의 데이터 API**: `POST /admin/sync/mock` 이 운영 환경에도 열려 있습니다(ADMIN 권한은 필요). 개발 프로필(`@Profile("dev")`)에서만 켜는 것을 권합니다.
- **서버 시작 시 동기화**: `SyncStartupRunner` 가 서버가 켜질 때마다 일정 동기화를 실행합니다. 서버가 여러 대면 모두 실행하고(저장은 중복 없이 처리됨), 공용 스레드 풀에서 돕니다. 별도 `TaskExecutor` 와 "한 대만 실행"을 고민하세요.
- **결과 DTO 의 `insertedSeatCount`**: 좌석은 선점할 때 만들어지므로 동기화 시점에는 항상 0 입니다. 의미 없는 값이라 응답에서 빼는 것을 권합니다(프론트 영향 확인 후).

## 10. 운영·배포·테스트

### OPS-1. 운영 설정 [확인] S2

- 저장소의 `docker-compose.yml` 은 DB 비밀번호가 평문이고, DB·Redis 포트가 모든 인터페이스에 공개되며(`5432:5432`, `6379:6379`), Redis 에 비밀번호가 없습니다. 이 구성을 서버에서 그대로 쓰면 인터넷에서 DB·Redis 에 접근할 수 있습니다(Redis 가 열려 있으면 이메일 인증 키 `TOKEN:RESET_PW:*` 도 위조할 수 있습니다). → 로컬 바인딩(`127.0.0.1:...`) 또는 내부 네트워크만 사용하고, 비밀번호는 환경변수로 받으세요. 이미지 태그는 `latest` 대신 버전 고정.
- HTTPS 가 없으면 로그인 비밀번호와 JWT 가 평문으로 오갑니다. 도메인 연결 후 인증서를 적용하세요.
- `server.port=80` 은 권한이 필요합니다(기본값이고 `SERVER_PORT` 로 바꿀 수 있음). 컨테이너·프록시 뒤에서는 8080 이 일반적입니다.
- 헬스체크(`/actuator/health`)와 기본 지표(요청 수, 대기열 길이, 선점 수)를 붙이면 장애를 빨리 알 수 있습니다.
- **DB 연결 풀**: 기본 HikariCP 의 크기와 타임아웃을 부하 테스트로 정하세요. 외부 API 를 트랜잭션 밖으로 뺀 지금은 풀 고갈 위험이 줄었습니다.

### TEST-1. 테스트 전략 [확인] S3

- 현재 `@SpringBootTest` 테스트는 **실제 DB·Redis(·외부 API)가 있어야** 돌아가고, 일부는 `payment`, `reservation`, `seat` 테이블을 `DELETE` 하며, 한 테스트는 하드코딩된 Redis 주소를 씁니다. 운영/개발 DB 를 가리킨 채 실행하면 데이터가 지워집니다.

## 11. 제안하는 처리 순서

| 단계 | 할 일 | 이유 |
|---|---|---|
| 1 | **DB 스키마를 SQL 로 저장소에 고정 (DB-1)**, UNIQUE·인덱스 | 이후 모든 것의 전제. 가장 먼저 |
| 2 | SEC-1 재설정 토큰을 회원에 묶기, SEC-2 시도 제한 | 계정 탈취. 코드가 작아서 빠르게 끝남 |
| 3 | BIZ-1 조건부 UPDATE + 영향 행 수 확인 | 돈과 좌석 정합성의 핵심 |
| 4 | BIZ-2 좌석별 호차(프론트와 함께), BIZ-4 선점 검증 | 잘못된 좌석 결제 방지 |
| 5 | Q-1 대기열 강제 + Q-2 입장 상태 정리 + Q-3 장애 정책 | 대기열이 실제로 보호하게 만들기 |
| 6 | TIME-1 시계·TTL 설정화, SCH-1 스레드·만료 해제 개선 | 선점이 제때 풀리게 |
| 7 | SSE-1 커밋 후 전송, 풀림 이벤트 | 화면이 현실과 맞게 |
| 8 | BIZ-3 주문 개념·환불, SEC-3 | 기능 완성도 |
| 9 | EXC-1 검증·예외 정리, OPS-1 운영 설정 | 서비스를 열기 위한 마무리 |
| 10 | TEST-1 Testcontainers 로 위 시나리오 자동화 | 이후 변경을 안전하게 |

### 각 단계의 완료 기준 (이 문장이 참이면 끝)

1. 새 DB 에 SQL 파일만으로 전체 앱이 뜨고, 같은 좌석을 두 번 INSERT 하면 DB 가 거부한다.
2. 다른 계정의 재설정 토큰으로는 비밀번호를 바꿀 수 없고, 인증번호를 6번 틀리면 잠긴다.
3. 같은 예약에 동시에 결제 요청을 보내도 결제 행은 1개다. 결제와 만료가 겹쳐도 "결제됨 + 좌석 판매됨"은 불가능하다.
4. 서로 다른 호차의 좌석을 함께 골라도 선택한 대로 잡히고, 출발한 열차에는 선점할 수 없다.
5. 토큰 없이 선점하면 거부되고, 만료된 토큰은 더 이상 입장으로 보이지 않으며, Redis 를 끄면 정해둔 정책대로 동작한다.
6. 선점 시간을 설정값으로 바꾸면 화면·에러 문구까지 따라 바뀌고, 외부 API 가 멈춰도 만료 해제가 돈다.
